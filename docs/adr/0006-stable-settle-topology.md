# ADR 0006 — คู่โอนต้องนิ่งเมื่อยอดลอยตามเวลา (star + `transferKey` 2 รูปแบบ)

- สถานะ: Accepted (แทนที่ส่วน "key ผูกทิศทาง + ยอด" ของ [ADR 0003](0003-transfer-key-amount-bound.md) เฉพาะกรณียอดลอย)
- วันที่: 2026-07-31

## บริบท

บิลโหมด `time` ที่ยังมีผู้ร่วมบิลที่ `leftAt == null` ทำให้ยอด **ลอยไปตามนาฬิกา**:
คนที่ยังนั่งอยู่รับสัดส่วนเวลามากขึ้นทุกวินาที ⇒ ยอดต่อคนขยับเอง แม้ผู้ใช้ไม่ได้แก้ข้อมูลอะไรเลย

อาการที่ผู้ใช้เจอ (รายงานเข้ามาเป็น "ปุ่มปิดวงหายเอง / กล่อง 🎉 จ่ายครบทุกคนแล้วหายเอง"):
ติ๊ก "โอนแล้ว" ครบทุกรายการ กล่องขึ้นแล้ว วางมือถือไว้ สักพักกลับมาดู กล่องหายไป ปุ่มปิดวงหายด้วย
ทั้งที่ไม่มีใครแตะข้อมูล — ต้นเหตุมี **สองชั้นที่ทับกันอยู่**:

1. **key ผูกยอด** — `transferKey` เดิมมียอดเงินอยู่ใน key (ADR 0003) ยอดลอยไปแค่ 1 สตางค์
   key ก็ไม่ match แล้ว ⇒ ติ๊กเดิมกลายเป็น "ยังไม่โอน" (แก้ก่อนหน้านี้ด้วย `Transfer.stamp`
   = ลายนิ้วมือของข้อมูลที่กำหนดยอด ไม่ผูกนาฬิกา)
2. **ตัวคู่โอนเปลี่ยนเอง** — `settleUp` แบบ greedy จับคู่จากลำดับ "ยอดมาก→น้อย" ของเจ้าหนี้/ลูกหนี้
   ซึ่งลำดับนั้นก็ลอยตามเวลาด้วย เวลาเดินไปไม่กี่ชั่วโมงลำดับสลับ หรือมีคนข้ามเส้นศูนย์
   (เจ้าหนี้กลายเป็นลูกหนี้) ⇒ **ชุดคู่โอนเปลี่ยนตัวคน** รายการที่ติ๊กไว้หายไปจากรายการทั้งแถว

ชั้นที่ 2 คือหัวข้อของ ADR นี้: แก้ชั้นที่ 1 อย่างเดียวไม่พอ เพราะแม้ key จะไม่ผูกยอดแล้ว
ถ้าคู่คนหรือทิศทางเปลี่ยน key ก็ยังคนละตัวอยู่ดี

## ตัวเลือกที่พิจารณา

1. **ยอดลอย → จับคู่แบบดาว (star) รอบศูนย์กลางที่เลือกจากข้อมูล + key ผูก "คู่คน" ไม่ผูกทิศ/ยอด** ← เลือก
2. คง greedy ไว้ แต่ตรึงลำดับด้วยเวลาอ้างอิงที่คงที่ — ยังพัง: greedy ให้ **หลายเส้นต่อคน** ได้
   (ลูกหนี้หนึ่งคนโอนให้เจ้าหนี้ 2 คน) พอยอดลอย การ "แบ่งเส้น" เปลี่ยนจำนวนเส้นเองแม้ลำดับตรึงแล้ว
3. star แต่ยังผูกทิศทางใน key (`${from}>${to}@stamp`) — ครึ่งเดียว: เคสที่เครื่องหมาย net พลิก
   (เจ้าหนี้ ↔ ลูกหนี้) ยังทำติ๊กหลุด วัดได้ **5.33%** ของเคสสุ่มที่วง ≤5 คน / **4.43%** ที่ ≤10 คน
   ซึ่งเท่ากับสัดส่วน "เคสที่เครื่องหมายพลิกจริง" เป๊ะ = ตัวถอดทิศทางรับน้ำหนักของบั๊กนี้จริง ไม่ใช่กันเผื่อ
4. หยุดยอดลอยไปเลย (freeze เวลาอ้างอิงตอนติ๊กครั้งแรก) — เปลี่ยนความหมายของโหมด `time`
   ที่ผู้ใช้ตั้งใจใช้ ("ใครอยู่นานจ่ายมาก" ต้องเดินตามเวลาจริงจนคนสุดท้ายกลับ)

## การตัดสินใจ

`settleUp(state, asOf?)` มี **2 โหมดการจับคู่** ตัดสินด้วย `amountsDrift(state)`
(= มีบิลโหมด `time` ที่ `billComplete` และมีผู้ร่วมบิลที่ยัง `leftAt == null`):

- **ยอดนิ่ง** → greedy min-transfer เดิม ไม่เปลี่ยนพฤติกรรม (ยังได้จำนวนรายการโอนน้อยที่สุด)
- **ยอดลอย** → **star**: ทุกคนที่ net ≠ 0 มี **เส้นเดียว** กับศูนย์กลางเดียว
  ยอดของแต่ละเส้น = net ของคนนั้นเอง (ผลรวม net = 0 อยู่แล้ว ⇒ ศูนย์กลางได้รับสุทธิเท่า net ตัวเอง)
  ศูนย์กลางเลือกด้วย `settleHub()` = เจ้าหนี้รายใหญ่สุด **ณ `referenceAsOf(state)`**
  (เวลาของเหตุการณ์ล่าสุดที่บันทึกไว้: สร้างบิล/มาถึง/กลับ) — เลือกจาก **ข้อมูล ไม่ใช่นาฬิกา**
  ไม่งั้นศูนย์กลางจะขยับเองเมื่อเวลาเดิน แล้วปัญหาเดิมกลับมาทั้งดุ้น
  ยอดเท่ากัน → ตัดสินด้วยรหัสสมาชิก (`byCode`) เพื่อให้ทุกเครื่องได้ศูนย์กลางเดียวกัน

`transferKey(t)` จึงมี **2 รูปแบบ** ตามว่ารายการนั้นมี `stamp` ไหม:

| กรณี | รูปแบบ key | ผูกกับอะไร |
|---|---|---|
| ยอดนิ่ง (ไม่มี `stamp`) | `` `${fromId}>${toId}@${ยอด 2 ตำแหน่ง}` `` | ทิศทาง + ยอดเงิน (ADR 0003 เดิม) |
| ยอดลอย (มี `stamp`) | `` `${idน้อย}|${idมาก}@${stamp}` `` | **คู่คน + ลายนิ้วมือข้อมูล** ไม่ผูกยอด ไม่ผูกทิศทาง |

- `stamp` = `splitStamp(state)` — FNV-1a สอง seed (64 บิต) ของทุกฟิลด์ที่กำหนดยอด
  (สมาชิก: `consumes`/`arrivedAt`/`leftAt` · บิล: หมวด/โหมด/ผู้ร่วม/คนจ่าย/เลี้ยง/ส่วนลด/service/vat/createdAt · เมนู: ราคา/ผู้ร่วม)
  **เรียงก่อน hash** → ลำดับแถวที่ต่างกัน (refetch/realtime) ให้ค่าเดียวกัน
  ชื่อ/พร้อมเพย์ไม่อยู่ใน stamp → แก้ชื่อแล้วติ๊กไม่หลุด
- ทิศทางไม่อยู่ใน key เพราะทิศทางเป็น **ผลลัพธ์ของยอดที่ลอย** เหมือนตัวเลขยอด
  (star การันตีว่ามีไม่เกิน 1 เส้นต่อคู่ ⇒ key ไม่ชนกันเอง)
- สองรูปแบบไม่มีทาง match ข้ามกัน (ตัวคั่น `|` vs `>` และค่าหลัง `@` — stamp ขึ้นต้น `t`, ยอดขึ้นต้นเลข/`-`)
  key ที่ไม่รู้จัก = "ยังไม่โอน" ตาม fail-safe เดิม ไม่ throw
- ผลพลอยได้: `commitPrune`/`pruneState` **prune ได้ทุกเคสแล้ว** ไม่ต้องยกเว้นบิลโหมด `time`
  เพราะ key ของยอดลอยนิ่งข้าม `asOf` ที่ต่างกัน (ยกเลิกข้อยกเว้นที่เขียนไว้ใน ADR 0003)

## ผลที่ตามมา

- **ตาข่ายกันเงินหาย (สำคัญ ต้องเข้าใจก่อนใช้)**: ตอนคนสุดท้ายติ๊ก "กลับแล้ว" `amountsDrift`
  กลายเป็น `false` ⇒ ยอดหยุดลอย ⇒ key ย้ายจากแบบ 2 กลับไปแบบ 1 (ผูกยอด)
  **ติ๊กชุดเดิมเป็นโมฆะทั้งชุด ต้องติ๊กใหม่บน "ยอดปิดจริง" ก่อนปิดวง**
  นี่คือสิ่งที่ทำให้ยอมแลกความหลวมของ key แบบ 2 ได้: ระหว่างที่ยอดยังลอย ติ๊กบอกแค่ว่า
  "คู่นี้เคลียร์กันไปรอบหนึ่งแล้วบนยอดชั่วคราว" แต่แอปจะไม่ปลดล็อกปุ่มปิดวงด้วยติ๊กชุดนั้น
  บนยอดสุดท้าย ทุกคู่ต้องยืนยันกันอีกครั้งบนตัวเลขที่นิ่งแล้ว
  วัดจากเคสสุ่ม: ทุกเคสที่ทุกคนกลับแล้วเป็นโมฆะจริง **1457/1457** (วง ≤5 คน) และ **1643/1643** (≤10 คน)
- **สิ่งที่แลกไป — key ยอดลอยไม่แยกทิศทาง**: ถ้า A ติ๊ก "A โอนให้ B แล้ว" แล้วต่อมาทิศพลิกเป็น
  "B โอนให้ A" ระบบยังนับว่าคู่นี้ติ๊กแล้ว (ยอดเปลี่ยนเป็นทิศตรงข้ามก็ไม่ปลดติ๊ก)
  ยอมรับได้เพราะ (ก) ระหว่างยอดลอยตัวเลขยังไม่ใช่ยอดจริงอยู่แล้ว (ข) ตาข่ายด้านบนบังคับติ๊กใหม่
  ก่อนปิดวงเสมอ — ไม่มีเส้นทางที่ทำให้แอป "อ้างว่าเงินโอนแล้ว" บนยอดปิดจริงโดยไม่มีใครติ๊ก
- **ต้นทุนจำนวนรายการโอน** ของ star เทียบ greedy (เฉพาะ state ที่ยอดลอย): **+0.14%** ที่วง ≤5 คน
  และ **+0.07%** ที่ ≤10 คน — คือเพิ่มขึ้นราว 1 รายการในบางวงที่มีเจ้าหนี้หลายคน แลกกับคู่โอนที่นิ่ง
- ผลที่วัดได้หลังแก้: ติ๊กหลุดจาก "เวลาเดินไปเอง 1 วัน / 30 วัน" = **0.00%** ทั้งวง ≤5 และ ≤10 คน
- **ยังพิสูจน์ไม่ได้**: fuzz ทำที่วง **≤10 คน** เท่านั้น · E2E ถูกบังคับเป็น local mode
  จึงไม่มีเทสอัตโนมัติครอบพฤติกรรมนี้ใน group mode (สองเครื่องพร้อมกัน)
- คนที่แก้ต่อ: **ห้ามประกอบ key เอง** ต้องผ่าน `transferKey(t)` เท่านั้น (มี 2 รูปแบบแล้ว)
  และห้ามคิดว่า `settleUp` เป็น greedy อย่างเดียว — ฟีเจอร์ที่พึ่ง "จำนวนโอนน้อยสุด"
  ต้องเผื่อโหมด star ด้วย
- ฟังก์ชันที่เกี่ยวข้องทั้งหมดอยู่ใน [../../src/domain/split.ts](../../src/domain/split.ts):
  `amountsDrift`, `splitStamp`, `referenceAsOf`, `settleHub`, `transferKey`, `settleUp`
