# ADR 0002 — คิดเงินบนสตางค์จำนวนเต็ม + เกลี่ยเศษแบบ largest remainder

- สถานะ: Accepted (เพิ่ม invariant "ผลลัพธ์ไม่ขึ้นกับลำดับ array" ภายหลัง — ดูท้ายไฟล์)
- วันที่: 2026-07-31

## บริบท
สูตรหารทั้งหมดเดิมคิดบน `number` หน่วยบาทแล้วปัด 2 ตำแหน่งตอนแสดงผล
ผลคือยอดที่โชว์บนจอ (ยอดต่อคน, สถานะ "ได้คืน/ต้องจ่าย") กับรายการโอนจาก `settleUp()`
คลาดกัน 1-2 สตางค์ในหลายเคส: ผลรวม net ของทุกคนไม่เป็น 0 พอดี, ยอดที่เจ้าหนี้จะได้รับ
ไม่เท่ากับผลรวมที่ลูกหนี้ต้องโอน เพราะแต่ละค่าถูกปัดแยกกัน (และ float 0.1+0.2 ก็มี noise ของตัวเอง)
โค้ดเดิมพยายามกลบด้วย threshold ลอย ๆ (`0.005`) ใน `settleUp` ซึ่งซ่อนอาการได้บางเคสแต่ไม่แก้ต้นเหตุ

เงินหาย/งอกทีละสตางค์เป็นเรื่องที่ผู้ใช้จับได้ทันที (โอนแล้วยอดยังไม่เป็น 0) และทำให้
`nothingOwed()` กับ checklist ดูเหมือนพัง

## ตัวเลือกที่พิจารณา
1. **คิดทุกอย่างเป็นจำนวนเต็มหน่วยสตางค์ แล้วเกลี่ยเศษแบบ largest remainder** ← เลือก
2. คงหน่วยบาทเป็น float แล้วขยาย threshold — ซ่อนอาการ ไม่แก้ต้นเหตุ ผลรวมยังไม่เป็น 0
3. ใช้ decimal library (เช่น decimal.js) — แม่นแต่เพิ่ม dependency ให้เลเยอร์ที่ตั้งใจให้ pure/เบา
   และยังต้องตัดสินใจเรื่องเกลี่ยเศษเองอยู่ดี

## การตัดสินใจ
- ยอดสุทธิภายในคิดเป็น **สตางค์จำนวนเต็ม** (`netBalanceCents`) แล้ว `computeNetBalances()`/`settleUp()`
  แปลงกลับเป็นบาทตอนคืนค่า → ทั้งสองฟังก์ชันมาจากฐานเดียวกัน ตรงกันตลอด
- ปัดด้วย `roundNetCents()` แบบ **largest remainder**: ปัดใกล้สุดแบบสมมาตรรอบ 0 ก่อน
  แล้วเกลี่ยเศษที่เกิน/ขาดทีละ 1 สตางค์ให้คนที่ปัดห่างค่าจริงมากสุดก่อน
  เสมอกัน → ให้ **ลูกหนี้รับเศษก่อน** (คนออกเงินจะได้คืนครบตามที่ควักจริง)
  เสมอกันอีก → ตัดสินด้วย **รหัสสมาชิก (`byCode`)** (เดิมเป็นลำดับแถวใน array — ดูภาคผนวก)
- **ลบ threshold `0.005` ออก** — ไม่ต้องมีแล้วเพราะไม่มีเศษ float ให้กลบ
- `round2()` ยังอยู่ ใช้สำหรับปัดตอนแสดงผล/ประกอบ `transferKey` (สมมาตรรอบ 0)

## ผลที่ตามมา
- ผลรวม net ของทุกคน = 0 พอดี และ ผลรวมยอดโอน = ผลรวมหนี้ = ผลรวมที่เจ้าหนี้ต้องได้ เป๊ะ
- กฎการเกลี่ยเศษเป็น **deterministic และไม่ขึ้นกับลำดับแถวใน `state.members`** อีกแล้ว
  (ข้อนี้เดิมเขียนว่า "ขึ้นกับลำดับ" — เป็นบั๊ก ไม่ใช่ข้อจำกัดที่ยอมรับ; แก้แล้ว ดูภาคผนวก)
- คนที่แก้สูตรต่อ **ห้ามกลับไปคิดบน float หน่วยบาทกลางทาง** และห้ามใส่ threshold กลับมา
  ถ้าเจอเลขเพี้ยน ให้ไปดูว่าจุดนั้นหลุดออกจากฐานสตางค์หรือเปล่า
- เอกสารเก่าที่ยังเขียนว่า "threshold 0.005 กันเศษ floating point" ถือว่าล้าสมัย (แก้แล้วใน SPEC + rules)

## ภาคผนวก (เพิ่มภายหลัง) — invariant: ผลลัพธ์เป็นฟังก์ชันของข้อมูล ไม่ขึ้นกับลำดับ array

**invariant ที่ต้องถือไว้ตลอด**: ยอดต่อคน / net / คู่โอน / `transferKey` ต้องขึ้นกับ **ข้อมูล** เท่านั้น
สลับลำดับแถวใน `state.members`, `state.bills`, `bill.items` แล้วผลต้องเหมือนเดิมทุกทศนิยม

ทำไมต้องเป็นกฎ ไม่ใช่ "รายละเอียดที่ยอมได้": ในโหมดกลุ่ม Postgres ไม่การันตีลำดับแถวเมื่อ query
ไม่ระบุ `order by` (ลำดับเปลี่ยนได้ตาม query plan/vacuum/index) ⇒ สองเครื่องในกลุ่มเดียวกัน
ได้ `members` มาคนละลำดับ ⇒ เศษ 1 สตางค์ตกคนละคน ⇒ net ต่างกัน ⇒ คู่โอน/key ต่างกัน
⇒ **คนหนึ่งติ๊ก "โอนแล้ว" อีกคนเห็น "ยังไม่โอน"** และปุ่มปิดกลุ่ม/กล่อง "จ่ายครบทุกคนแล้ว" หายเอง
กระทบ **ทุกโหมดการหาร** (equal/itemized/time) เพราะอยู่ที่ชั้นเกลี่ยเศษ ไม่ใช่ชั้นสูตร

สิ่งที่แก้ (สองจุด — **จุดเดียวไม่พอ**):

1. **tiebreak ชั้นสุดท้ายเป็นรหัสสมาชิก** — `largestRemainder()` เดิมตัดสินตอนเศษเสมอกันเป๊ะด้วย
   `a.index - b.index` (ตำแหน่งแถวใน array) เปลี่ยนเป็น `byCode(a.id, b.id)`
   และ greedy sort ใน `settleUp()` ที่ตอนยอดเท่ากันก็ผูกลำดับแถวเหมือนกัน → เพิ่ม `byCode` เป็น tiebreak
   `byCode` เทียบตาม code unit **ห้ามใช้ `localeCompare`** ในเลเยอร์โดเมน เพราะผลต่างกันตาม locale
   (จะกลายเป็น "ผลขึ้นกับภาษาของเครื่อง" แทน)
2. **`sumStable()` — เรียงค่าก่อนบวก** ใช้ 6 จุดในเส้นทางคิดเงิน (subtotal, ผลรวมน้ำหนัก, ยอดต่อเมนู,
   `billIssues`, `roundNetCents`, `timeShares`) เพราะ **การบวก float ไม่ commutative**:
   `0.1+0.2+0.3 ≠ 0.3+0.2+0.1` ในบิตท้าย ต่างกันระดับ `1e-13` ก็พลิก `Math.round` ไปอีกทาง
   ในเคสที่ยอดตกลง .5 สตางค์พอดี (เช่น 4 คนหาร ฿236.58 → 4254.5 สตางค์) ⇒ เศษ 1 สตางค์ย้ายคน

ตัวเลขที่วัดได้ (fuzz seed คงที่, กลุ่ม ≤5 และ ≤10 คน):

| | ก่อนแก้ | แก้ tiebreak เท่านั้น | tiebreak + `sumStable` |
|---|---|---|---|
| ติ๊กหลุดเพราะลำดับแถว (≤5 คน) | 30.17% | 0.050% | 0.000% |
| net ต่างกันเพราะลำดับแถว (≤5 คน) | — | 0.075% | 0.000% |
| ติ๊กหลุดเพราะลำดับแถว (≤10 คน) | 47.75% | — | 0.000% |

**ต้นทุนศูนย์**: จำนวนรายการโอนเฉลี่ยเท่าเดิมทุกทศนิยม และค่าสูงสุดเท่าเดิม (4 ที่ ≤5 คน / 9 ที่ ≤10 คน)
เพราะเปลี่ยนแค่ "ตอนเสมอกันเป๊ะเลือกใคร" ไม่ได้เปลี่ยนวิธีจับคู่

ฝั่งข้อมูลแก้ควบกัน (ไม่ใช่ทางเลือก — โดเมนนิ่งแล้ว แต่ **รายชื่อบนจอยังสลับตำแหน่งเอง** ถ้าไม่ทำ):
`fetchGroupState()` ใส่ `.order()` + tiebreak `id` ทั้ง 3 ตาราง, เรียงซ้ำฝั่ง client (`sortByTimeThenId`),
มี `selectOrdered()` fallback สำหรับ project เก่าที่ยังไม่มีคอลัมน์เวลา, และ `createGroup` ส่ง `seqStamp()`
ไล่ทีละ 1 ms ตอน migrate เพราะ **`now()` ของ Postgres คงที่ทั้งทรานแซกชัน** — insert ชุดเดียว
ได้ `created_at` เท่ากันหมด `order by created_at` เฉย ๆ จึงไม่ช่วย
index ฝั่ง DB อยู่ใน [`../../infra/supabase/patch-005-stable-order.sql`](../../infra/supabase/patch-005-stable-order.sql)

**ยังพิสูจน์ไม่ได้**: fuzz ครอบกลุ่ม ≤10 คน · ผลข้ามเครื่องจริงใน group mode ไม่มีเทสอัตโนมัติ (E2E บังคับ local mode)

**ผลกระทบต่อผู้ใช้ที่มีอยู่**: หลัง deploy คนที่ติ๊ก "โอนแล้ว" ค้างไว้อาจต้องติ๊กใหม่ **รอบเดียว**
เพราะการเกลี่ยเศษอาจย้าย 1 สตางค์ → key เดิมไม่ match — เป็น fail-safe ตามเจตนา [ADR 0003](0003-transfer-key-amount-bound.md) ไม่ใช่บั๊ก
