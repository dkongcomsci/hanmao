# Rules: Domain (สูตรหาร / โมเดลข้อมูล)

ขอบเขต: `src/domain/**`, `src/utils/**` (+ ผู้เรียกทุกคนต้องรู้กฎ `asOf`)

## เวลา: กฎ `asOf`

- [src/domain/split.ts](../../src/domain/split.ts) เป็น **pure ทั้งไฟล์ — ห้ามมี `Date.now()`**
- ฟังก์ชันที่ต้องรู้ว่า "ตอนนี้กี่โมง" (คนที่ยัง `leftAt = null` ในบิลโหมด `time`)
  รับ **`asOf?: number`** เป็นพารามิเตอร์สุดท้าย; ไม่ส่งมา = ใช้ `bill.createdAt` เป็นเวลาอ้างอิง
  ปัจจุบันคือ `computeBill`, `computeTotals`, `computeNetBalances`, `settleUp`
- **ผู้เรียกหา `const now = Date.now()` ครั้งเดียวต่อ render แล้วส่งค่าเดียวกันเข้าทุก call**
  (ทุกหน้าใน `app/` ที่คิดเงินทำแบบนี้แล้ว พร้อมคอมเมนต์กำกับ)
  เหตุผล: ถ้าแต่ละ call อ่านนาฬิกาเอง ยอดต่อคนกับรายการโอนในหน้าจอเดียวกันจะคิดจากเวลาต่างกัน
  → เลขไม่ตรงกัน, `transferKey` ไม่ match กับที่ติ๊กไว้, เทสไม่ deterministic
- ฟังก์ชันใหม่ที่ต้องใช้เวลา ต้องรับ `asOf` แบบเดียวกัน ห้ามอ่านนาฬิกาในเลเยอร์โดเมน

## ตัวเงิน

- คิดภายในเป็น **จำนวนเต็มหน่วยสตางค์** แล้วแปลงกลับเป็นบาทตอนคืนค่า
  ผลรวม net ของทุกคนต้องเป็น 0 พอดี และตรงกับ `settleUp()` เสมอ
- เศษปัดไม่ลงตัวเกลี่ยแบบ **largest remainder** (เสมอกัน → ลูกหนี้รับเศษก่อน → เสมอกันอีก → **รหัสสมาชิก** `byCode`)
- **ห้ามใส่ threshold แบบ `0.005` กลับมา** — เอาออกไปแล้วโดยเจตนา
  ([ADR 0002](../../docs/adr/0002-integer-cents-largest-remainder.md))
- `round2()` ใช้ตอนแสดงผล/ประกอบ key เท่านั้น

## ผลลัพธ์ต้องไม่ขึ้นกับลำดับแถวใน array (invariant)

ยอดต่อคน / net / คู่โอน / `transferKey` ต้องเป็นฟังก์ชันของ **ข้อมูล** เท่านั้น —
สลับลำดับ `state.members` / `state.bills` / `bill.items` แล้วผลต้องเท่าเดิมทุกทศนิยม
(โหมดกลุ่มดึงแถวจาก Postgres ที่ลำดับไม่การันตี ⇒ ถ้าผลต่างกัน คนหนึ่งเห็น "โอนแล้ว" อีกคนเห็น "ยังไม่โอน"
และปุ่มปิดกลุ่ม/กล่อง "จ่ายครบทุกคนแล้ว" หายเอง)

- **ห้ามใช้ตำแหน่งแถว (index) เป็น tiebreak** — ชั้นสุดท้ายทุกที่ใช้ `byCode(a.id, b.id)`
  (ทั้งใน `largestRemainder` และการ sort ของ `settleUp` โหมด greedy)
- **ห้ามใช้ `localeCompare` ในเลเยอร์โดเมน** — ผลต่างกันตาม locale ⇒ ผลจะขึ้นกับภาษาของเครื่อง; ใช้ `byCode` (เทียบตาม code unit)
- **ห้ามบวก float ตรง ๆ ในเส้นทางคิดเงิน** — ใช้ `sumStable()` (เรียงค่าก่อนบวก) เพราะการบวก float
  ไม่ commutative ต่างกัน `1e-13` ก็พลิก `Math.round` ในเคสที่ยอดตกลง .5 สตางค์พอดี ⇒ เศษ 1 สตางค์ย้ายคน
- กระทบ **ทุกโหมดการหาร** (equal/itemized/time) เพราะอยู่ที่ชั้นเกลี่ยเศษ ไม่ใช่ชั้นสูตร
  ([ADR 0002 ภาคผนวก](../../docs/adr/0002-integer-cents-largest-remainder.md))

## `settleUp` มี 2 โหมด

ตัดสินด้วย `amountsDrift(state)` (= มีบิลโหมด `time` ที่ `billComplete` และมีผู้ร่วมบิลที่ยัง `leftAt == null`):

- **ยอดนิ่ง** → greedy min-transfer เดิม
- **ยอดลอย** → **star**: ทุกคนที่ net ≠ 0 มีเส้นเดียวกับ hub เดียว (`settleHub` เลือกจากข้อมูลผ่าน
  `referenceAsOf` **ไม่ใช่จากนาฬิกา**) + ติด `stamp` ให้ทุกรายการ
  เหตุผล: greedy จับคู่จากลำดับยอดที่ลอยตามเวลา ⇒ คู่โอนเปลี่ยนตัวคนเอง ⇒ ติ๊กหลุด
  ([ADR 0006](../../docs/adr/0006-stable-settle-topology.md))

ฟีเจอร์/เทสที่พึ่งสมบัติ "จำนวนโอนน้อยที่สุด" ต้องเผื่อโหมด star ด้วย (star แพงกว่าเล็กน้อยโดยเจตนา)

## ติดตามการโอน

- key ของรายการโอนมี **2 รูปแบบ** ตามว่ามี `stamp` ไหม:
  - ไม่มี `stamp` (ยอดนิ่ง) → `` `${fromId}>${toId}@${round2(amount).toFixed(2)}` `` ผูก **ทิศทาง + ยอด**
    ยอดเปลี่ยน = ติ๊กเดิมเป็นโมฆะเอง ([ADR 0003](../../docs/adr/0003-transfer-key-amount-bound.md))
  - มี `stamp` (ยอดลอย) → `` `${idน้อย}|${idมาก}@${stamp}` `` ผูก **คู่คน + ลายนิ้วมือข้อมูล**
    (`splitStamp` = FNV-1a สอง seed ของฟิลด์ที่กำหนดยอด **ไม่ผูกนาฬิกา**) ไม่ผูกยอด ไม่ผูกทิศทาง
- ประกอบ key ด้วย `transferKey()` เท่านั้น **ห้ามต่อสตริงเองในหน้าจอ/store** (มี 2 รูปแบบแล้ว ยิ่งห้าม)
- **ตาข่ายกันเงินหาย**: ทุกคนติ๊ก "กลับแล้ว" → ยอดหยุดลอย → key ย้ายกลับไปแบบผูกยอด
  ⇒ ติ๊กชุดเดิมเป็นโมฆะทั้งชุด **ต้องติ๊กใหม่บนยอดปิดจริงก่อนปิดกลุ่ม** — ห้ามเขียนโค้ด/เอกสารที่พยายาม "กู้" ติ๊กชุดนั้น
- เช็ก "เคลียร์หมดแล้ว" ด้วย `nothingOwed()` (ไม่มีรายการโอนเลยก็นับว่าไม่มีหนี้ค้าง)
  ไม่มี `allSettled()` แล้ว
- key รูปแบบเก่า/ยอดเก่าที่ค้างอยู่ต้อง **ไม่ match เฉย ๆ** (นับเป็น "ยังไม่โอน") ห้าม throw
  — ยอมให้ผู้ใช้ติ๊กซ้ำ ดีกว่าอ้างว่าเงินถูกโอนแล้วโดยไม่จริง
  (สองรูปแบบไม่ match ข้ามกันอยู่แล้ว: ตัวคั่น `|` vs `>`, ค่าหลัง `@` ขึ้นต้น `t` vs เลข/`-`)

## เกณฑ์ "บิลเข้าสรุป"

- เกณฑ์อยู่ที่ `billIssues()` ที่เดียว (คืนข้อความไทยให้ UI แสดง) และ
  `billComplete() = billIssues(...).length === 0`
- เพิ่มเงื่อนไขใหม่ต้องเพิ่มข้อความบอกผู้ใช้ด้วยเสมอ — ห้ามทำให้บิลหายจากสรุปแบบเงียบ ๆ

## โมเดลข้อมูล

- `*Ids` ที่เป็น array ว่าง = **"ทุกคนที่เข้าเงื่อนไข"** (`bill.memberIds` → ทุกคนที่ `consumes` เข้ากับ `category`;
  `item.participantIds` → ทุกคนในบิล) — ห้ามเปลี่ยนความหมาย และห้ามเติม id ทุกคนลงไปแทน
- `paidById` = คนออกเงิน **ของแต่ละบิล อาจคนละคน** — requirement หลัก
- ฟิลด์ใหม่ควรเป็น **optional** เพื่อไม่พัง state เดิมที่ผู้ใช้บันทึกไว้ในเครื่อง
